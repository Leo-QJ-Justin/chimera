# chimera v0.2 — Beads integration into `/start-feature`

**Status:** approved (brainstorming complete, awaiting writing-plans)
**Date:** 2026-05-05
**Branch:** `feat/v0.2-beads-integration`

## Motivation

chimera v0.1 ships an orchestrating `/start-feature` command that chains Superpowers' brainstorm/plan/execute skills with planning-with-files' on-disk persistence layer, plus a branch-enforcement `PreToolUse` hook. What v0.1 doesn't ship is a **dependency-aware backlog** — there is no way to ask "what's the next unblocked phase across this and other in-flight features?" without keeping that state in your head.

`bd` (Steve Yegge's beads CLI, v1.0.3, upstream `gastownhall/beads`) provides exactly this: a typed task graph with hash-based IDs, dependency edges, and an embedded Dolt DB committed to the repo (`.beads/`) that survives `/clear`, compaction, and multi-week gaps. A research recon ruled out adopting `pprice/beadpowers` (8 stars, 4 months stale, thin) or `withzombies/hyperpowers` (Superpowers fork with no `bd` invocations despite the tagline) as dependencies. The recommendation: chimera owns its own `bd` verbs directly. v0.2 implements that.

## Goals

1. Integrate `bd` into the `/start-feature` rhythm so every feature's epic + phases are tracked in beads automatically.
2. Move branch verification from Step 5 to Step 0 of `/start-feature` to prevent the "spec-write blocked because we were on main" failure mode that surfaced during chimera's own bootstrap session.
3. Maintain clean separation of artifacts:
   - **Superpowers plan** = HOW (TDD steps per phase)
   - **beads graph** = WHAT'S NEXT (claim order + dependencies)
   - **`task_plan.md` dashboard** = WHERE (current phase + bd IDs for recovery)

## Non-goals

- **No unit tests / CI / lint setup for chimera in v0.2.** chimera v0.1/v0.2 are markdown-instruction plugins; there is no code to unit-test. Manual smoke procedure documented instead. Revisit when chimera ships actual code.
- **No fix to the CWD-vs-file-scope hook bug.** Today the chimera branch hook reads `git rev-parse` in the harness CWD, not the edited file's git context. v0.3 candidate; out of scope here.
- **No `Stop` hook warning for uncommitted `bd ready` items.** Deferred until real-world usage informs the false-positive rate.
- **No `/bd-init-project` standalone command.** `bd init` is a one-liner the user can run directly when needed.

## Architecture

v0.2 is a single behavioral edit: `commands/start-feature.md` is rewritten to embed `bd` invocations at the right pipeline stages.

```
chimera/
├── commands/start-feature.md     ← REWRITTEN (only behavioral change)
├── hooks/hooks.json              ← unchanged
├── CHANGELOG.md                  ← v0.2.0 entry added
├── .claude-plugin/plugin.json    ← version bump 0.1.0 → 0.2.0
└── docs/
    ├── superpowers/specs/2026-05-05-v0.2-beads-integration-design.md   ← THIS FILE
    ├── superpowers/plans/2026-05-05-v0.2-beads-integration.md          ← from writing-plans
    └── testing/smoke.md          ← NEW: manual end-to-end verification procedure
```

The `bd` binary is called via Bash from within the agent's interpretation of `start-feature.md`. No plugin-level Bash scripts. No new hooks.

## The new `/start-feature` flow

Pipeline goes from 7 steps to 8. **Steps 0, 2, and 4 are new or repositioned**; the others are unchanged.

### Step 0 — Verify branch *(NEW position; was Step 5 in v0.1)*

- Run `git rev-parse --abbrev-ref HEAD`.
- If `main` or `master`: refuse, instruct user to create a feature branch (`git checkout -b feat/<name>`) or invoke `superpowers:using-git-worktrees`. Halt the rhythm.
- Otherwise proceed.

**Rationale:** v0.1 ran the spec-write of Step 1 before branch verification at Step 5, so any spec-write attempt while on main/master was blocked by the chimera branch hook. This caused friction we hit twice during chimera's own bootstrap. Promoting verification to Step 0 eliminates the class.

### Step 1 — Brainstorm *(unchanged)*

Invoke `superpowers:brainstorming`. Produces design doc at `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`. User-approval gate as before.

### Step 2 — Bootstrap beads *(NEW)*

1. **Preflight:** `command -v bd >/dev/null`. If missing, print the install hint to stderr and abort the rhythm:
   ```
   curl -fsSL https://raw.githubusercontent.com/gastownhall/beads/main/scripts/install.sh | bash
   ```
2. **Init if absent:** if `.beads/` does not exist in the repo, run `bd init` silently. The `.beads/` directory will be committed alongside the first epic.
3. **Create the epic:**
   ```
   bd create "<feature title from brainstorm>" --type epic -p 0 \
     -d "Spec: docs/superpowers/specs/<topic>-design.md"
   ```
4. **Capture `EPIC_ID`** from `bd create` output. Preferred: `bd create ... --json` if v1.0.3 supports it. Fallback: `awk '/Created issue:/ {print $4; exit}'` on stdout. **Documented gotcha:** do not use a greedy regex like `bd-[a-z0-9]+` — beads issue IDs have the form `bd-<lowercase-prefix>-<hash>` with multiple dashes; the regex used during chimera bootstrap matched only `bd-<prefix>` and silently passed the prefix as the epic ID. The implementation plan must verify `--json` support and select the right path.

### Step 3 — Write implementation plan *(unchanged)*

Invoke `superpowers:writing-plans`. Produces bite-sized TDD plan at `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`.

### Step 4 — Sync plan → beads *(NEW)*

For each phase in the Superpowers plan, in plan order:

1. ```
   bd create "<phase title>" --parent $EPIC_ID -p 1 \
     -d "Files: <comma-separated file paths from the Superpowers plan's Files: section>
         Acceptance: <one-to-two sentence summary of what 'done' looks like>"
   ```
   Default priority is **P1** (high) for all phases. P0 is reserved for emergency/blocker phases the user manually upgrades.
2. Capture each `PHASE_ID` (same extraction approach as Step 2.4).

For sequential phases (Phase N depends on Phase N-1):

3. `bd dep add <PHASE_ID_n> <PHASE_ID_n-1>` — encodes ordering as dependency edges so `bd ready` surfaces them in the right sequence.

Then:

4. **Hold `EPIC_ID` and the ordered list of `PHASE_ID`s in working memory.** Step 5 will write them into `task_plan.md` when it scaffolds the dashboard. This is the recovery anchor: on `/clear` or session death, re-reading `task_plan.md` restores the bd context.

### Step 5 — Scaffold persistence files *(modified content, not mechanism)*

Invoke `planning-with-files:planning-with-files` to scaffold `task_plan.md`, `findings.md`, `progress.md` (mechanism unchanged). Then convert `task_plan.md` to the chimera dashboard format, **populating it with the `EPIC_ID` and `PHASE_ID`s captured in Step 4**. Each phase entry references its bd ID, for example:

```markdown
## Current Phase
Phase 2 [bd-chimera-7nq] — Token issuer

## Phases
### Phase 1 [bd-chimera-9hk] — Schema migration
- **Status:** complete
### Phase 2 [bd-chimera-7nq] — Token issuer
- **Status:** in_progress
```

The ≤30-line constraint is unchanged so the planning-with-files PreToolUse `head -30` re-injection captures the whole dashboard.

### Step 6 — Execute *(modified: claim/close lifecycle around each phase)*

For each phase, in the order surfaced by `bd ready --json`:

1. `bd update <phase-id> --claim` (atomic; prevents duplicate claims by parallel sessions).
2. Run TDD steps from the Superpowers plan for this phase. Use `superpowers:subagent-driven-development`.
3. `bd close <phase-id> "<resolution>"` once tests green and committed.
4. Update `task_plan.md` dashboard's Phase status to `complete`.

### Step 7 — Wrap up *(unchanged)*

Invoke `superpowers:finishing-a-development-branch`. The epic remains `open` after wrap-up so the user can add follow-up tasks; user closes it explicitly when done with follow-ups.

## Failure modes

| Failure | Behavior |
|---|---|
| `bd` not on PATH | Step 2 prints install hint to stderr and aborts the rhythm. User installs, re-runs `/start-feature`. |
| `bd init` fails (e.g. permissions) | Abort; surface the `bd` error verbatim. |
| `bd create` (epic) fails | Abort. The epic is the foundation; without it nothing else makes sense. |
| `bd create` (phase) fails partway through Step 4 | Continue creating the remainder; log the failed phase. User reconciles via `bd list --parent <epic>` afterward. |
| `bd update --claim` fails (already claimed) | Warn-and-continue. Implies a parallel session/agent — surface for awareness, do not block. |
| `bd close` fails | Warn; leave the issue open for manual close. |
| Plan has zero phases (degenerate) | Skip Step 4, log "no phases to sync"; epic stands alone. |

## Testing strategy

- **Manual end-to-end smoke** (v0.2): in a throwaway git repo, run `/start-feature` on a trivial fake feature (e.g. "add `hello.txt` with greeting"). Verify each pipeline stage produces the expected artifacts: feature branch, spec doc, plan doc, `.beads/` dir with one epic and one issue per phase, dependency edges between sequential phases, claim/close lifecycle visible in `bd show <phase-id>`. Procedure documented in `docs/testing/smoke.md`.
- **Out of scope (v0.3+):** unit tests, CI, lint. chimera does not yet have code that warrants any of these.

## Acceptance criteria

A feature run through v0.2's `/start-feature` should produce, by Step 7:

1. A feature branch (verified at Step 0) — never on `main`/`master`.
2. A committed spec at `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`.
3. A committed plan at `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`.
4. A `.beads/` directory committed to the repo with one epic and one issue per phase.
5. Dependency edges between sequential phases visible via `bd show <phase-id>`.
6. A `task_plan.md` at repo root, ≤30 lines, including the `EPIC_ID` and ordered `PHASE_ID`s.
7. All phases either `closed` (work done) or remaining `open` (work not yet started); none orphaned in `in_progress` after their work is done.
8. The epic itself remains `open` after Step 7 (user closes manually when fully done with any follow-ups).
9. `docs/testing/smoke.md` exists and accurately describes the procedure that produced the run.
10. `CHANGELOG.md` has a v0.2.0 entry; `plugin.json` version is `0.2.0`.

## Open questions / known carry-forward

- **Hook is CWD-scoped, not file-scoped.** chimera's branch hook reads `git rev-parse` in the harness CWD, not the edited file's git context. Hit twice during chimera's bootstrap session (CWD was inside the chimera git repo on `main`, which blocked edits to `~/.claude/settings.json` even though that file is not in chimera). v0.3 candidate.
- **`bd create --json` support unverified.** v1.0.3 may or may not support `--json` on `create`. The implementation plan must verify this and pick the right capture mechanism (`--json` vs `awk`).
- **`Stop` hook warning for uncommitted `bd ready` items** — deferred. Will revisit once chimera has been used on 3+ real features and the false-positive rate is observable.
