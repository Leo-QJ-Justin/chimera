# Pipeline Skeletons & Utils — Design Spec

> Design spec for chimera. Written 2026-07-30. **Status: approved (maintainer
> review, 2026-07-30).** Evidence base: the five trawl reports in
> docs/research/ (2026-07-30-pipeline-trawl-*.md) per the trawl plan
> (2026-07-30-pipeline-templates-trawl-plan.md). Decisions below were made
> in maintainer synthesis review, 2026-07-30.

## Goal

Ship ready-to-use ML pipeline skeletons and configured utils as chimera
deliverables: a `skeletons/` directory holding project scaffolds (two
tiers × per-stack modules) plus a shared utils package, wired into
`/design-project`'s SCAFFOLD step.

## Decisions

Each decision records the verdict and the evidence that forced it.

**D1. Config: Hydra composition + pydantic validation.**
Hydra owns file composition, config groups, CLI overrides, and Optuna
sweeps (AIAP canon; Atlas tuning note; USEP spec). Pydantic validates the
composed config: shared base models subclassed per pipeline,
`extra="ignore"` + warn-on-extra, `mode="after"` cross-field validators,
and `log_config_defaults` (the "why did it use 42?" warner) — the salvage
from dynamic-simu-model's config layer. Its global-overrides-local
deep-merge is explicitly rejected.

**D2. Structure: framework-agnostic core + per-stack modules, two tiers.**
- Core (every project): config, logging, MLflow wrapper, run artifacts,
  seeding, the one-data-path rule.
- Stack modules: tabular/sklearn (Micron + Atlas pipelines-note evidence),
  deep learning (Sembcorp + assignment5 evidence), time series overlays
  (windowing, walk-forward). Modules are pluggable; no per-framework
  skeleton forks (three frameworks in the corpus make forks a maintenance
  trap).
- Tiers: **assessment-weight** (Micron's floor + its cheap restores:
  model save/load, metrics seam, promoted `run_cv`) and
  **production-weight** (four-pipeline shape with shared utils hoisted —
  fixing dynamic-simu-model's duplication).

**D3. MLflow: single-tracker wrapper.**
DualMLflowLogger's dual-tracker design is an Azure workaround; rejected.
Keep its four portable ideas: never-fail-the-pipeline (tracking failures
log a warning, never abort), batched logging APIs, idempotent registry
create, and the enabled-check living *inside* the factory (three
inconsistent call sites in dynamic-simu-model, one silently wrong).
Adopt from AIAP canon: MLflow-optional contract (bool threaded, no-op
when off) — but with plain kwargs passthrough, never the `co_varnames`
filter (it silently ate a peer's checkpoint logging). Adopt from
dengfeng_zhou: per-epoch artifact namespacing (`checkpoints/epoch_{n}`),
`input_example` → model signature, properly threaded init flag.
MLflow-less fallback: a structured CSV/JSONL metrics sidecar plus a
curve-plotting helper that reads it — no one ever parses prose logs again
(Sembcorp `plot_log` is the cautionary evidence).

**D4. One data path (the Sembcorp symmetry rule).**
Training, evaluation, and serving all consume the same sample-building
path; eval predictions are generated by feeding the inference pipeline.
Rationale: easiest debugging in the corpus (Sembcorp), and the structural
fix for train/serve skew (the `#wrong?` re-typed de-normalisation constant
at inference). dynamic-simu-model's divergent per-pipeline reimplementations
are the counterexample.

**D5. Data/training boundary (medallion-aligned).**
- Data pipeline: load → stateless clean → **stateless** feature
  engineering. Outputs the **full** gold table plus split-enabling keys
  (timestamps, entity/group IDs, duplicate-group markers). Never splits.
- Training pipeline: owns the split (protocol from config), all fitted
  preprocessing, and the model.
- The fitted/stateless line is the contract: if it needs `.fit()`, it is
  not data-pipeline code. (Micron drew this correctly;
  dynamic-simu-model's fitted preprocessor inside the data pipeline did
  not.)
- Frozen canonical holdouts (e.g. "test touched once") are declared as
  boundary dates or ID lists in config / `data/splits/`, never by
  physically splitting in the data layer.

**D6. Tabular composition: sklearn Pipeline + ColumnTransformer.**
The industry-standard layer for the sklearn stack. It absorbs the
`fit_transform/transform` half of leakage-as-architecture (per-fold
refitting free via `cross_val_score`/`GridSearchCV`), the one-artifact
serialization (preprocessing + model in one `joblib`/MLflow model), and
the `get_config` round-trip (`sklearn.clone`). Custom code keeps only what
sklearn can't do: stateless clean pre-split, row-dropping/dedup (
transformers can't drop rows or touch y), decision-table feature choices,
CV protocol selection. `set_output(transform="pandas")` on.

**D7. DL trainer: assignment5 `train_model` as the base.**
Evolve `origin/qjjustin_leo:assignment5/src/train.py`:
- factor inlined loops into `run_one_epoch` / `evaluate` helpers (the
  maintainer-preferred epoch abstraction; also attested in the Atlas NN
  helper note) — trainer becomes a thin loop + callbacks;
- `early-stopping-pytorch` for patience + best-checkpoint persistence
  (external library over hand-rolling; already proven in a5);
- `ReduceLROnPlateau` over StepLR / hand-rolled schedulers;
- checkpointing generalized to `monitor: {name, mode}` (single monitored
  metric default; second best-file opt-in); checkpoint = dict with
  `state_dict` + optimiser state + epoch + metrics (never whole-module
  pickle); NaN guard kept (Sembcorp); resume semantics a named config
  choice `resume: continue | from_best`;
- keepers from Sembcorp: sample-weighted metric accumulation, per-phase
  stage timing (as a `stage_timer` context manager logging to logger +
  MLflow), `subsample_frac` via `RandomSampler`, overfit-single-batch
  sanity check (Atlas), `set_seed` util (Atlas Reproducibility note,
  verbatim + DataLoader generator), device setup (cuda→mps→cpu +
  `PCI_BUS_ID` pinning before torch import, auto-DataParallel),
  DataParallel-safe checkpoint loading, partial-checkpoint transfer
  loading with the imported/random-init audit (shape filter enabled),
  `count_parameters`, `log_remark` free-text run note.
- Plain torch; no Lightning (corpus is plain torch; the harness is 80% of
  what Lightning adds).

**D8. Split reproducibility contract.**
Persist realized split **membership**, not just the recipe: a `splits`
artifact per run (member keys per split; fold assignments for CV;
boundary dates *plus* realized membership for temporal). Stable row keys
(`entity_id`, `timestamp`, or durable sample ID) — never positional
indices, which break silently when the gold table is regenerated. Log a
membership-hash fingerprint as an MLflow param for at-a-glance
split-identity comparison. Loaders accept a split artifact: seed+protocol
is the generator, the artifact is the record. (Corpus status: Micron
persisted membership as full data copies; dynamic-simu-model persisted
only the recipe; USEP reserved `data/splits/` unimplemented; Sembcorp's
file-path lists were stable keys by accident.)

**D9. CV / evaluation protocol: per-problem-type decision table, not
dogma.** i.i.d. tabular → nested CV or per-fold-fresh-pipeline CV;
time series → walk-forward with temporal cutoff (never shuffled);
final-fit doctrine (refit-on-all vs untouched holdout) chosen per project
and recorded in the project's decision table. Ships as a small reference
table in the skeleton docs, consumed by the writing-plans decision-table
convention.

**D10. Run artifacts (from dynamic-simu-model, hoisted to core).**
One timestamp per run threaded everywhere; `base/<ts>/` output dirs;
`latest.json` + `best.json` pointers with `resolve_artifact_path` as the
sole read path; `best` generalized to `(metric, mode)`; post-merge config
snapshot into the run dir; git + environment run-info; `_make_serialisable`
for JSON dumps; `metadata.json` reload envelope (model_type, timestamp,
environment, feature_columns, hyperparameters, files map, embedded
upstream-config blob) with metadata-first reconstruction and exact
feature-order validation on load.

**D11. Feature contracts.**
Assembled feature arrays ship a **manifest** (name, slice, source, dtype,
scale) as a logged artifact — total width becomes a computed invariant,
never a magic 133. Per-feed window specs are declarative: cadence, window
length, inclusive/exclusive of anchor, floor rule, expected length,
`on_short: pad|skip|error`. Divisor normalisation
(`normalization: {feature_group: divisor}`) is a first-class config mode
for physically-bounded feeds (eliminates scaler persistence and skew).
Sample-level validity checks skip the sample, never the run, and surface
per-reason rejection counters as run metrics.

**D12. Logging.**
`logger = logging.getLogger(__name__)` everywhere; configuration once at
the entry point, never at import or inside `train()`; package logger, not
root; pure helper modules never log; scalars via logger, pre-formatted
blocks via print; tz-aware formatter; log file path returned so the run
can upload it as an artifact; JSON logging config (AIAP canon
`logging.yaml` with level-split rotating handlers) as the production-tier
option with the log-dir rebinding + degrade-to-basicConfig bootstrap.

**D13. Quality gates.**
Two-tier pre-commit (ruff check+format at commit; pyright + pytest at
push, env prefix parameterised); ruff line-length 90 with N803/N806
ignored for ML naming; tests derive constants from schema defaults (never
user config); don't re-test pydantic; `tmp_path` round-trip tests for
pointer/artifact utils; `.gitattributes` normalizing line endings; uv as
the env/packaging default; li_yang-style Dockerfile (BuildKit cache
mounts, two-phase `uv sync --locked`, non-root) and dengfeng-style
compose (required settings no defaults, env injection, ro mounts) for the
serving tier.

## Skeleton inventory and scaffold trees

Three project kinds, two tiers. Scaffolds are the trees `/design-project`
SCAFFOLD stamps out; `{project}` is the package name.

### A. Assessment-weight (any stack)

```
{project}/
  main.py                  # decision-record entry point (constants + comments)
  pyproject.toml           # uv; [tool.ruff] minimal block
  README.md
  data/raw/                # committed if small; data/processed/ gitignored
  notebooks/eda.ipynb      # pure pandas/seaborn, imports nothing from src
  notebooks/training.ipynb # imports src; run_cv from src, not inline
  src/
    pipelines/
      data_pipeline/pipeline.py        # clean (stateless) + gold output
      training_pipeline/
        pipeline.py                    # split + fit + evaluate orchestrator
        classes/base_*.py + models     # ABC: fit/predict/tune + save/load
        modules/{evaluation,cv}.py     # metrics dict; promoted run_cv
    utils.py               # set_seed, save/load helpers, splits artifact
tests/                     # optional at this tier
```

Floor additions over Micron: model save/load, a ~20-line MLflow seam,
`splits.json`, run_cv in src. Everything else stays deliberately dropped.

### B. Production-weight tabular / time series

```
{project}/
  main.py  README.md  pyproject.toml  .pre-commit-config.yaml  .gitattributes
  configs/
    config.yaml            # base: paths, seed, mlflow, logging
    data_pipeline.yaml  training.yaml  inference.yaml
    model/*.yaml           # config group per model family
    logging.yaml
  data/{raw,processed,splits}/         # processed+splits gitignored
  notebooks/
  outputs/                 # gitignored; outputs/<pipeline>/<ts>/
  src/{project}/
    core/                  # THE shared boundary — pipelines import, never copy
      config.py            # hydra entry helpers + pydantic bases + log_config_defaults
      logging_setup.py
      tracking.py          # MLflow wrapper + metrics sidecar
      run_artifacts.py     # timestamp, pointers, metadata envelope, snapshot
      seeding.py  splits.py  timing.py
    pipelines/
      data_pipeline/       # load → stateless clean → stateless features → gold
      training_pipeline/   # split → sklearn Pipeline (fitted) → model → eval
      inference_pipeline/  # same sample path + fitted artifact
    features/              # feed specs, windowing, manifest (time series overlay)
  tests/                   # per-pipeline suites + schema contract tests
```

### C. Production-weight deep learning

Same tree as B, with the training pipeline swapped for the DL module:

```
    pipelines/training_pipeline/
      trainer.py           # thin loop: run_one_epoch → evaluate → callbacks
      loops.py             # run_one_epoch, evaluate, predict (metric-injectable)
      callbacks.py         # EarlyStopping(lib), checkpoint {monitor,mode}, LR
      checkpointing.py     # save dict schema, DataParallel-safe load, partial load
      datasets/            # Dataset with constructor validation, block registry
      device.py            # setup_device: pinning, cuda→mps→cpu, DataParallel
      sanity.py            # overfit-single-batch check
```

Serving (either tier B/C, opt-in): FastAPI four-file split (settings-driven
versioned prefix, `/healthz`, module-level model load, required settings
without defaults), compose with ro mounts, Dockerfile per D13.

## Revision R1 (maintainer review of first build, 2026-07-31)

Maintainer feedback on the first built trees supersedes parts of D2 and
the scaffold trees above:

**R1.1 Two scaffold types, no tiers.** The deliverables are an **AI
Application scaffold** (future task) and one **ML Pipelines scaffold**.
The assessment / production / production-dl tier split is dropped; there
is one production-level ML scaffold.

**R1.2 Four pipelines.** `data_pipeline`, `training_pipeline`,
`inference_pipeline`, and a dedicated **`evaluation_pipeline`** (consumes
inference outputs plus ground truth: metrics report, residual/error
triage, run comparison). D4 unchanged: evaluation feeds through the
inference path for predictions.

**R1.3 Production level by default.** MLflow integration is first-class
and enabled by default in the base config (sqlite backend); run
artifacts, config snapshots, split records all standard. "Bare minimum"
is explicitly not the goal of the scaffold.

**R1.4 dynamic-simu-model layout per pipeline.** Each pipeline directory
carries `classes/` (stateful objects behind an ABC), `modules/`
(stateless functions), `configs/` (that pipeline's YAML), and
`pipeline.py` (orchestrator). `core/` remains the shared utils package
all pipelines import.

**R1.5 Trainer abstraction.** `training_pipeline/classes/` defines
`BaseTrainer` (fit / predict / save / load contract) with concrete
trainers configured externally via the Hydra model group — e.g.
`SklearnTrainer`, `LightGBMTrainer`, `TorchTrainer` (the DL loops,
callbacks, checkpointing, and device modules become TorchTrainer's
internals). The train pipeline orchestrator stays thin: load gold →
split → build trainer from config → fit → evaluate hook → persist.

**R1.6 (follow-up, 2026-07-31): per-pipeline configs + evonik trainer
contract.** Each pipeline also carries its own `configs/` directory
(dynamic-simu-model layout confirmed against the repo), with one shared
`configs/shared/base.yaml` at root reached via Hydra searchpath. Every
trainer has a config file tagged to it as a Hydra group
(`training_pipeline/configs/trainer/<name>.yaml`) composed into the
training config — selection is `trainer=<name>` on the CLI. The
`BaseTrainer` contract follows the maintainer's evonik-temp
`BaseModel` (the more complete variant): abstract `_build_model()` +
`_get_param_space(trial)` + `train`/`predict`; concrete on the base:
`evaluate(metrics=[str|callable])`, `cross_validate` (fresh model per
run), and `hyperparameter_tune` (full Optuna loop). Merged with existing
decisions rather than copied verbatim: metadata-first save/load with a
recorded `model_class` check (not bare joblib), CV splitter chosen from
the split config mode per D9 (not hardcoded `TimeSeriesSplit`), seed
threaded from config, optuna as a guarded optional dependency.

**R1.7 (follow-up, 2026-07-31): no medallion jargon.** The layered-output
concept stays, the naming goes: no "bronze/silver/gold" in class names,
file names, config keys, or docs. The data pipeline saves **stage
checkpoints** — config lists which stage boundaries to persist
(`checkpoints: [cleaned, features]` → `data/processed/<stage>.parquet`)
— and its final output is the processed/model-input table
(`processed_path`), which the training pipeline consumes. Where earlier
sections of this spec say "gold table", read "processed table".

**R1.8 (follow-up, 2026-07-31): the scaffold is self-contained.**
`core/` lives *inside* the scaffold (`ml-pipelines/src/PROJECT/core/`)
with its test suite in the scaffold's `tests/`, not as a separate
`skeletons/core/` copied in at scaffold time. Rationale: after R1.1
there is exactly one consumer; the copy-at-scaffold-time indirection
made the in-repo template non-runnable and added a botchable step. If a
future scaffold needs shared utils, factor then — don't pre-abstract
for a consumer that doesn't exist.

**R1.9 (follow-up, 2026-07-31): diagnostic artifacts, split by what they
need.** The first build logged numbers and models but drew no figures —
matplotlib was not even a dependency, and LightGBM/XGBoost discarded their
eval curves entirely. Diagnostics are now first-class, split across the two
pipelines by their input rather than by their subject matter:

| Diagnostic | Needs | Pipeline | Applies to |
|---|---|---|---|
| Training curves | per-iteration history | training (post-fit) | torch, lightgbm, xgboost |
| Feature importances | `estimator.feature_importances_` | training (post-fit) | random_forest, lightgbm, xgboost |
| Coefficients | `estimator.coef_` | training (post-fit) | logreg |
| SHAP beeswarm / bar | model internals + a data sample | training (post-fit) | all but torch; config-gated |
| Confusion matrix | hard predictions | evaluation | classification |
| ROC / PR curves | `proba_*` columns | evaluation | classification |
| Calibration | `proba_*` columns | evaluation | binary classification |
| Residuals, predicted-vs-actual | hard predictions | evaluation | regression |

The line is model-based vs prediction-based. SHAP needs the estimator, not
its outputs, so it cannot live in the evaluation pipeline; the confusion
matrix needs only the predictions table, so putting it in training would
mean training scoring a sample a second time — the thing D4 exists to
prevent. Trainers stay tracking-free and plotting-free: a booster now
*captures* its eval record into `history` (via `record_evaluation` /
`evals_result()`, flattened by `modules/history.py`), and the orchestrator
replays that into MLflow step-wise exactly as it already did for torch.

**Hand-rolled over `mlflow.models.evaluate`:** the evaluate API wants
fluent global run state, and its score-based artifacts want a loadable
model rather than a predictions table, whereas the core
`Tracker` drives `MlflowClient` with an explicit `run_id` precisely to
avoid fluent state — and these figures must also work with tracking off.
Hand-rolled sklearn + matplotlib gives a curated artifact set and works
offline. No new tracking surface was needed: both pipelines already upload
their whole run directory, so anything written into `<run_dir>/plots/`
mirrors to MLflow for free.

**Dependencies:** `matplotlib` becomes a **core** dependency (curves are
part of what a run is expected to produce, so they must not be what a
missing install silently drops); `shap` is the optional `explain` extra,
guarded with the same `_import_<lib>()` pattern the trainer families use —
absent, the step logs one line and is skipped. Kill switches:
`diagnostics.enabled` / `diagnostics.shap.enabled` (training),
`plots.enabled` (evaluation). Every diagnostic is individually wrapped in
the warn-and-continue pattern: a figure that cannot be drawn costs the run
one log line, never the artifacts it already wrote.
